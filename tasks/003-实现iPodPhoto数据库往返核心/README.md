## 为什么从 Photo 开始

iPod Photo 的传统 `iTunesDB` 适合先建立数据库 Reader、Model、Writer 和 Validator 的共同骨架。它不是只为一台机器写的临时代码：后续 Classic 会复用共同骨架，再增加自己的记录差异和 hash58。

## 本轮结论

FooPodBridge 不以“复刻 iTunes、一次支持所有 iPod”为目标。完整兼容还涉及连接方式、文件系统、数据库世代、签名、artwork、固件差异和实机安全验证；仅按“第几代”判断不足以可靠写入。

数据库系统按以下层次扩展：

1. **共同往返核心**：有界解析记录、建立稳定模型、保留未知数据、验证结构并安全重新生成数据库。
2. **数据库格式配置**：描述传统 Photo、Classic 等格式的记录和校验差异，不把所有差异堆进一个型号分支。
3. **设备能力配置**：根据已取得的设备属性、数据库版本和固件证据决定可用能力；营销名称只作为辅助信息。
4. **验证等级**：依次区分“结构已知、fixture 往返通过、实机只读通过、实机写入通过”，不能把较低等级宣传成完整支持。

因此，架构为传统 iPod 家族保留扩展位置，但正式写入仍只对白名单中的、由项目维护者逐台验证的 iPod Photo 和 iPod Classic 开放。未知或未经验证的设备最多只读，并由服务层拒绝写入。早期 FireWire 机型、shuffle 及其他数据库家族只有在以后获得真实需求、合法证据和对应硬件验证时才建立独立配置；iPod touch/iPhone 不进入本项目。

## 任务 003 的实际边界

本任务只完成共同往返核心和 iPod Photo 格式配置，以脱敏 fixture 验证：

- 正常数据库可读取并通过结构验证；
- 无修改往返保持语义和未知数据；
- 截断、越界、长度冲突和非法引用被明确拒绝；
- 在内存模型中增删虚拟曲目与普通 playlist 后可以稳定往返；
- 所有测试只操作仓库 fixture 和电脑临时目录，不连接或写入实机。

Classic 的格式差异与 hash58 留在任务 004。更广型号兼容是以后按证据增加配置的路线，不是任务 003 的交付承诺。
