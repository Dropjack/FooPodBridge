## 1. 用户能得到什么

插入已经能被 Windows 作为磁盘访问的 iPod 后，FooPodBridge 自动识别设备、读取容量和现有曲库，并说明哪些信息已经验证、哪些仍未知。拔出后停止读取，重新插入重新核对。整个任务只读。

任务 005 提供永久的 Core、服务接口和 FooPodBridge Preferences 中的只读设备信息页，供用户核对真实识别结果、曲目/播放列表数量和错误原因。完整的曲目列表、封面浏览和 FooCrate Devices 工作区按原路线由后续任务完成。

信息页首版使用英文文案，包含设备选择、识别家族、状态与原因、容量/可用空间、证据等级、曲目/普通及 Smart playlist 数量、身份是否充分、签名检查结果以及只读 Refresh。无设备时显示真实空状态。没有初始化、修复、导入、删除或 Eject 命令。

## 2. 输入、判断和输出

1. 输入来自 Windows 当前设备节点、磁盘/卷映射和挂载信息；启动时也检查已经连接的设备。
2. 建立候选卷和物理设备的关联，再读取候选卷固定位置的设备属性与数据库；不遍历普通磁盘上的个人文件。
3. 结合硬件证据、设备属性和数据库头选择候选家族、只读解析器和证据状态。
4. 有界读取数据库，通过 Reader/Validator 后生成内存中的不可变曲库快照。
5. 服务发布当前设备集合及版本；信息页只显示快照，不自己打开设备文件。
6. 失败时丢弃未完成结果、关闭句柄、发布明确原因；连接本身不修复或创建文件。

所有写入能力均为 false，已有服务写请求返回明确的 unsupported/preflight blocked 结果，不存在能执行的计划。

## 3. 全目标家族注册表

必须有以下 23 个代际条目，并保留“目标 iPod 已识别、具体代际未知”的结果，不能依赖当前手头设备删减条目。

| 家族 | 独立代际条目 | 候选数据库路线 | 本任务能力边界 |
| --- | --- | --- | --- |
| 早期全尺寸 | 1G、2G、3G、4G | 传统 iTunesDB | 结构可验证时只读，否则 FormatPending；完整 profile 留任务 009 |
| Photo/Color、Video | Photo/Color、5G、5.5G | 传统 iTunesDB | 同上，不能把当前 5.5G 样本当通用 Writer |
| Mini | 1G、2G | 传统 iTunesDB | 同上 |
| Classic | 2007、2008、2009 | 6G/hash58 候选 | 验证实际 DB 与签名需求，不按 Classic 名称强套 profile |
| Nano | 1G、2G | 传统 iTunesDB | 只读；完整代际 profile 留任务 009 |
| Nano | 3G、4G | 6G/hash58 候选 | 使用任务 004 Reader 和签名检查能力 |
| Nano | 5G、6G、7G | CDB/SQLite/签名独立路线 | FormatPending，列明任务 011 的缺失能力 |
| Shuffle | 1G、2G、3G、4G | iTunesSD/ShadowDB 独立路线 | FormatPending，列明任务 010 的缺失能力 |

每个条目至少记录：稳定 family/profile 标识、代际、证据匹配条件及来源、可能的数据库路径/类型、签名需求、文件系统限制、Reader 是否可用、能力缺口和证据引用。实际 Reader 可用性与 Writer 可用性分开。

证据由 profile/型号/能力和测试记录定位；一份 Nano 4 fixture 通过不提高所有 Classic/Nano 的实机等级。缺少证据用 unknown 表达，不捏造 StructureKnown 或实机结论。只读采集过原始文件不等于本任务已完成 DeviceReadVerified。

## 4. 正向识别与身份

- Windows 磁盘/卷必须能关联到当前设备节点；USB 和早期 FireWire 路径都在目标范围，不能只扫描 USB 或只接受 removable 标志。
- 不能把 Apple 厂商号、USB 产品号前缀、盘符、卷标、显示名或一个 iPod_Control 目录单独当作充分证明。
- 固定历史来源确认的非 touch 硬件身份与一致的存储映射可以证明设备类别；已有设备文件/数据库须进一步交叉核对。未知硬件映射、复制到 U 盘的数据库或矛盾证据保持 UnidentifiedVolume。
- 具体代际无法唯一判断时显示 Unknown generation 或候选范围，不按容量或用户名称猜测。iPhone/touch/iPad 明确排除。
- SysInfo 为空或缺失不直接拒绝硬件证据充分的 iPod；任务 004 已证明 Nano 4 的 PnP 身份可用于私有签名交叉验证，但该结论不能推广为“任何 PnP 尾部都是 hash58 密钥”。
- 物理身份、卷身份、挂载代次、快照版本和签名密钥分开建模。盘符/磁盘编号只供本次定位，不是永久物理身份。
- 物理身份不足或冲突时只发布本次挂载有效的 opaque token 与 identity incomplete 原因，不假装跨重连稳定；永不授予写入。
- 完整硬件序列号、FireWire GUID 和卷路径只在必要的内部读取过程中使用，不出现在公开服务标识、日志、导出或 Git 中。

## 5. Windows 访问边界

设备适配器先注册到达/移除通知，再枚举现有接口，对通知与枚举重复结果去重。回调只更新失效标记并安排后台工作，不进行数据库 I/O。实现采用公开 SetupAPI/CfgMgr32 与存储/卷查询 API；卷到磁盘关系通过系统报告核对，不能从路径字符串猜测。

所有设备文件仅以读取权限打开，系统查询按最小访问权限执行。禁止写权限句柄、创建目录、修复、格式化、锁卷/卸载卷、设置属性、SCSI 私有配置、iTunes/Apple Mobile Device 依赖以及设备文件上的临时缓存。

固定相对路径必须被限制在已核对的候选卷内；拒绝越界路径、重解析跳转和不一致映射。读取错误区分不存在、拒绝访问、共享冲突、短读、移除、内容变化和资源超限，不把读取失败当成空库。

设备通知与主动 Refresh 驱动刷新，不后台循环扫描音频、哈希全部媒体或自动刷新评分。一次操作对同一失败条件最多尝试三次，仍失败后显示原因并等待明确 Refresh 或新的挂载事件；不得无限重试旧盘符。

## 6. 状态与失败结果

先判定设备是否存在及身份是否可信，再检查文件系统、恢复记录、数据库存在性、格式能力和内容有效性。主要状态与细化 reason 分开，保留已取得的诊断事实。

| 状态 | 条件 | 本任务结果 |
| --- | --- | --- |
| NotMounted | 已识别目标设备节点，但没有可访问存储卷 | 说明存储卷前置条件；不配置磁盘模式 |
| UnidentifiedVolume | 候选卷不能被正向识别，或身份/映射矛盾 | 只读诊断；不发布可信 Library |
| UnsupportedFileSystem | 目标设备的文件系统不在当前可靠读取范围 | 明确文件系统原因，不建议格式化 |
| FormatPending | 目标已识别，但格式/版本/能力未实现或证据不足 | 设备保持可见，说明缺失 Reader/profile；已有可验证只读数据单独标能力 |
| Initializable | 满足蓝图的正向身份、健康卷、明确 profile 和活动实验/验证任务条件，但主 DB 缺失 | 仅报告资格；本任务没有初始化命令，也不自动补足任务授权 |
| ReadyReadOnly | 现有 DB 结构/引用有效且只读快照可生成 | 发布 Library；全部写能力仍关闭 |
| DatabaseCorrupt | 已支持格式出现截断、越界、非法引用，或取得正确签名输入后验证失败 | 不当空库覆盖；保留诊断并停止发布当前可用 Library |
| RecoveryRequired | 有版本、身份与操作阶段可验证的本项目未完成提交记录 | 只报告恢复需求，不在 005 执行恢复 |

补充规则：

- 没有连接设备时发布空设备集合，不虚构一台 NotMounted 设备。
- 主 DB 缺失且尚不具备 Initializable 条件时返回 FormatPending + database missing / initialization prerequisites missing；存在但长度为零的 DB 是损坏，不能当缺失。
- 对已支持传统结构，无密钥可以结构只读；签名状态必须是 not checked + input unavailable，不能报验证通过或仅因此判损坏。未知格式仍是 FormatPending。
- 权限、共享占用、短读与资源超限是读取失败原因，沿用服务 error 语义，不误报 DatabaseCorrupt。无法证明固件/分区损坏时不能猜报 RestoreRequired。
- 发现不明 .tmp/.bak 文件不能推断 RecoveryRequired，更不能删除；任务 007 定义恢复记录后接入正式解析。本任务测试可注入恢复检测结果，但生产不能伪造已支持的恢复协议。
- 当前实现不产生 ReadyWritable。有效空 Library 是 ReadyReadOnly，数量为零，而不是 Initializable。

## 7. Library 快照和现有 Core 的补齐

复用任务 003/004 Reader、Validator 与 profile。早期传统只读可使用 TraditionalPreserveOnly，不因此宣布某代 Writer 已完成。Shuffle/Nano 5+ 不尝试套用传统 Reader 来制造成功。

快照至少包含 track ID/可用 persistent ID、原始标题/艺术家/专辑、已验证的设备相对路径、Music/Audiobook/其他或未知媒体类型、playlist ID/名称/类型及有序成员引用。原始数据库中有其他媒体时单独报告数量，不把 Video/Podcast 静默改成 Music，也不宣称管理它们。

当前 Core 尚未公开 Media Kind；005 按现有已审计传统记录来源补充只读投影与测试，不改写原始数据。不明字段或旧版本缺少该字段时保留 unknown，不靠 Genre/扩展名猜测。

Smart playlist 只发布已有类型和成员，不重算、不编辑规则。Artwork 在本任务仅报告文件/关联信息的可用性，未解析部分明确不可用；完整 ArtworkDB 解码、封面显示与管理沿任务 015 实现，不以空图片冒充成功。

元数据只通过正常曲库服务提供给本地消费者，不进入诊断。所有数量明确区分原始 track 总数、Music/Audiobook/其他/未知、master Library 与普通/Smart/不透明 playlist，避免把系统列表重复计数。

采用现有有界解析限制。读取前后核对挂载身份和文件状态，读取过程中有变化则丢弃结果；Refresh 重新读取并更新数据库指纹，不能保证在没有通知/Refresh 时感知外部软件的全部改动，也不把快照当设备独占锁。

## 8. 代次、并发与释放

- 每次挂载分配新代次，盘符复用、重新连接和身份/卷映射变化使旧代次失效。
- 同一挂载刷新产生新快照版本。只发布完整结果，后台旧任务不得覆盖较新状态。
- 移除通知或读取返回设备消失时立即在服务当前集合失效该设备，取消未完成工作；旧快照对象可以供消费者释放，但不能代表当前在线状态。
- 新的路径解析请求必须带设备 token、挂载代次和快照版本，并再次确认有效性；不能把旧盘符长期缓存给消费者后承诺安全。
- 多设备可见，读取任务有界调度；取消一个设备的工作不影响另一台。短期读取结束即关闭句柄，不为信息页长期持有设备文件。
- UI 订阅取消、窗口关闭、服务关闭均让晚到回调失效。停止接收工作后取消 I/O、回收 worker、注销通知；不强杀线程、不让回调访问已销毁对象。

## 9. 服务合同和信息页

现有 ABI 1.0 的类、GUID、虚函数顺序和已有枚举数值保持兼容；不能给旧接口直接增加虚函数。新家族、细化状态、证据、Library 和刷新能力通过新的可查询扩展接口与新 GUID 提供，并更新合同版本说明。

旧消费者仍能查询服务与基本只读快照；新家族在旧接口中安全映射为 unknown，缺失扩展的消费者明确显示不可用。新消费者必须检测扩展能力，不能猜测内存布局。

Core 不含 foobar SDK；适配层发布服务并把回调送回 foobar 主线程。FooCrate 在 005 不改代码、不复制 Core。信息页只订阅服务，以实际快照生成可检查结果；原有 provider 不再固定返回不存在。

## 10. 隐私、验证与批准点

诊断只包含家族/profile、状态/原因码、计数、能力是否可用和证据引用。默认不输出设备名称、序列号、用户路径、曲名、playlist 名、数据库原文或可跨会话追踪设备的原始指纹。Windows 错误文本也要先移除路径和输入值。

自动检查和人工验收按 [`VALIDATION.md`](VALIDATION.md) 执行。实现后的完成状态只能是“实现完成待验收”；用户明确核对通过后才进入 006。

本次请用户核对一个整体范围：按本规格实现全家族自动发现、只读 Library 服务、热插拔处理与永久设备信息页，并执行电脑侧测试、Debug/Release 构建、foobar-dev 开发检查及新的独立 FooPodBridge 候选包交付。实际连接设备的检查在需要时说明只读动作；设备写入不属于本规格。
