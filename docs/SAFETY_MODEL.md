# FooPodBridge 设备写入安全模型

- 状态：核心原则已批准；备份保留和清理交互等待任务 000 决策
- 日期：2026-08-25
- 架构：[`ARCHITECTURE.md`](ARCHITECTURE.md)

## 1. 威胁模型

目标设备使用旧式磁盘模式和可能的 FAT32 数据卷。即使机械硬盘已换成 CF、SD 或 SSD，原生 iPod OS 仍依赖原分区与文件系统语义。项目必须面对：

- USB 2.0 较慢，不能用无意义的重复复制换取表面安全；
- FAT32 没有事务日志和快照；
- 中途拔线、掉电、设备重置或转接板异常；
- 盘符复用、同型号多设备和一次挂载中的身份变化；
- 磁盘满、4 GiB 单文件限制、短写、Flush 或重命名失败；
- 数据库已引用但文件不存在，或文件存在但数据库未引用；
- Classic 数据库 hash58 错误导致设备看起来为空；
- 未理解记录被 Writer 丢弃，破坏 iTunes/固件仍使用的数据；
- 用户同时从两个 UI 发起操作或在事务中请求弹出。

安全优先级：旧数据库可恢复 > 数据库与引用一致 > 不留下孤立文件 > 速度与便利。

## 2. 设备身份门槛

每次写请求携带：

- 稳定设备身份；
- 当前挂载代次；
- 型号与能力矩阵版本；
- 当前数据库指纹；
- 预检时的目标卷与文件系统信息。

开始复制前和提交数据库前都重新核对。盘符相同但设备身份或代次变化时必须终止，不能继续写“看起来还是 E:”的卷。

只有实机验证表中的 Photo 和 Classic 可以进入 Writable。其他设备保持 Unsupported/ReadOnly，UI 没有本地开关可以绕过服务拒绝。

## 3. 第一次实机写入门槛

第一次对每台物理设备写入前，当前任务必须：

1. 记录不包含完整公开序列号的设备身份、型号、容量、固件、文件系统和数据库类型；
2. 让用户保存可恢复的 `iPod_Control` 备份，或按已批准工具验证现有备份；
3. 只读解析并重新序列化到电脑临时目录，证明不触碰设备也能完整往返；
4. 用数据库比较器说明哪些字节/记录预计变化；
5. 选择一首用户允许导入和删除的测试音频；
6. 明确该任务允许的唯一写入动作和人工恢复步骤。

未经本任务明确授权，不因设备已经连接就自动测试写入。

## 4. 操作计划

任何修改先生成不可变 `OperationPlan`。计划至少包含：

- 设备与数据库指纹；
- 曲目、源文件和目标 namespace；
- 直接复制/拒绝/转码决定；
- 预计新增与释放空间以及安全余量；
- 重复项、命名和 playlist 冲突；
- SoundCheck、gapless、封面和 Audiobook 处理结果；
- Smart Playlist 规则能力检查；
- 会创建、修改、删除的数据库实体与设备文件；
- 警告、阻断原因和可取消阶段。

UI 只提交经过预检的计划。执行时任何关键前提变化都使计划失效并重新预检。

## 5. 批量导入事务

```text
Prepared
→ CopyingMedia
→ BuildingDatabase
→ ValidatingDatabase
→ BackingUpDatabase
→ WritingDatabaseTemp
→ VerifyingDeviceDatabase
→ Committing
→ Cleaning
→ Completed
```

### 5.1 音频写入

1. 整个拖放/发送动作形成一个批次；运行中的后续请求进入队列，不能并发改同一设备。
2. 每首源音频只通过 USB 写入一次，目标位于最终 `Fxx` 目录中的 FooPodBridge 临时名称。
3. 写入过程中同时统计源字节与校验状态，不为正常路径额外完整读取一次设备文件。
4. 关闭前调用系统 Flush；关闭后核对设备文件大小和计划记录。
5. 同目录改为最终内部名称。该操作只改变目录元数据，不重新复制大文件；FAT32 下不假定掉电原子性，所以数据库仍未引用该文件。
6. 单曲失败按计划决定中止整个批次或保留其他成功项；该策略由用户决策冻结，不能 UI 各自实现。

完整音频读回哈希只用于开发实机验证、诊断模式或已检测到存储异常，不作为每次普通导入的固定成本。

### 5.2 数据库生成与提交

1. 全批音频准备结束后，在电脑内存/本地临时目录只生成一次新数据库。
2. Writer 输出后由独立 Reader 重新解析，检查记录数、稳定 ID、引用、playlist、Smart Playlist、SoundCheck、gapless、封面索引与设备能力。
3. Classic 在此阶段生成并验证 hash58。
4. 备份设备现有关键数据库和提交元数据；准确位置与保留数量由决策清单冻结。
5. 新数据库以临时名称写入设备，Flush 后完整读回。数据库远小于音频，正常路径允许完整比较与重新解析。
6. 只有读回数据库验证通过，才进入提交窗口。
7. 提交保留可识别的旧数据库备份，再把新数据库切换为正式名称。FAT32 不能提供真正多文件原子事务，因此保存恢复记录并定义每个重命名点的启动恢复规则。
8. 提交后从设备正式路径重新读取 Library，确认固件将要看到的状态与计划一致。

数据库不能每复制一首曲目就重建一次；一个用户批次最多提交一次。

## 6. 删除事务

删除设备曲目采用“先数据库、后音频”：

1. 解析目标曲目仍被哪些普通/Smart Playlist 引用；
2. 用户明确选择只移除 playlist 引用，或从设备 Library 删除；
3. 生成不再引用目标的数据库并执行完整验证/备份/提交；
4. 提交成功后删除已无引用的音频和相关资源；
5. 文件删除失败时数据库仍可用，结果记录为可清理孤立文件；
6. 数据库提交失败时不删除音频。

不提供把“从 playlist 移除”模糊显示为“Delete”的界面。

## 7. 播放列表与 Smart Playlist 事务

- 普通 playlist 只保存设备 track ID 引用，引用目标必须存在于 master Library。
- Smart Playlist 规则和初始成员同时验证；不支持的字段/运算符阻断保存。
- 修改现有 Smart Playlist 必须保留项目尚未编辑的有效规则与未知字段。
- 若固件不能 Live Update 某项规则，UI 必须明确其刷新语义，不能声称实时。
- 一次 playlist 编辑与其缺失曲目导入属于同一个操作计划和一次数据库提交。

## 8. 中断结果

| 中断位置 | 设备上可能状态 | 恢复原则 |
| --- | --- | --- |
| 复制音频前 | 原状态 | 无需恢复 |
| 音频临时文件写入中 | `.tmp` 或短文件，旧 DB 未引用 | 下次连接识别并按批准策略清理 |
| 音频已改最终名、DB 未提交 | 孤立音频，旧 DB 可用 | 清理或在恢复计划中继续提交 |
| 本地 DB 构建/验证失败 | 新文件可能孤立，旧 DB 可用 | 不进入提交；报告并清理 |
| 设备临时 DB 写入失败 | 旧 DB 正式路径仍在 | 删除临时 DB，保留旧状态 |
| 数据库重命名提交窗口中断 | 旧/新/备份名称组合之一 | 读取恢复记录和候选 DB，选择最后一个完整验证通过版本 |
| DB 已提交、音频清理失败 | 新 DB 可用，存在孤立文件 | 报告 CleaningRequired，不回滚有效 DB |

不能只根据文件名时间选择数据库；恢复前必须解析、校验和核对设备指纹。

## 9. 取消

- Preparing/Copying 阶段可以请求取消；当前系统写调用返回后进入安全取消点。
- Building/Validating 阶段可以取消并丢弃本地结果。
- Committing 阶段不立即中断关键重命名序列；先完成到一个可恢复边界，再报告取消结果。
- 取消不是“假装什么也没发生”。结果明确列出已复制、已提交、已清理和待清理项目。

## 10. 弹出与并发

- 同一设备最多一个写事务；其他写请求排队或被明确拒绝。
- 读取 UI 可以继续显示事务开始时的快照，但标记 Updating，不能基于旧快照发起冲突操作。
- 弹出请求在无事务时执行；有事务时只能选择等待或在安全点取消后弹出。
- 设备被物理拔除时立即失效全部句柄和快照，不重试旧盘符。

## 11. FAT32 与文件限制

- Windows 可用的目标设备预计是 FAT32 WinPod；HFS/HFS+ MacPod 在 Windows 无可靠原生读写路径时显示不支持。
- FAT32 单文件约 4 GiB 上限必须在预检阶段阻断，尤其检查超长 M4B/Audiobook。
- 不依赖大小写区分临时/正式文件；临时命名使用不可冲突前缀和操作 ID。
- 路径、目录项和可用空间在执行前后复核；不把 Windows 格式化 UI 的 32 GB 创建限制误当成设备容量上限。

## 12. 性能要求

- 音频正常路径只进行一次 USB 写入；
- 元数据、封面、SoundCheck 和 gapless 分析可在复制前或复制期间使用电脑 CPU 并行准备；
- 同一设备的 USB 写入保持有序，不为并行数字制造随机寻址和更差稳定性；
- 每批只构建、写入和提交一次数据库；
- 数据库允许完整读回验证，音频默认使用写入状态、Flush 和大小检查；
- UI 分阶段显示 Copying、Updating Library、Verifying 和 Cleaning，让用户知道数据库步骤没有卡死；
- 性能测试分别报告音频吞吐、数据库构建时间、设备 DB 写入/读回时间，不能只给总耗时。

## 13. 隐私与备份

- 自动测试 fixture 必须脱敏：设备名称、序列号、用户路径、曲目名和私人 playlist 按规则替换，同时保持结构关系。
- 真实备份、设备捕获和诊断包默认位于 Git 忽略目录。
- Release 日志不输出完整本地路径、设备序列号、曲库内容或数据库二进制。
- 备份位置、数量、保留期限和用户清理入口由 `decisions/USER_DECISIONS.md` 决定；无论选择如何，都不能让第一次写入没有可恢复备份。
